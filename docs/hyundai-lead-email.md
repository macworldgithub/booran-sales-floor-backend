# South Morang Hyundai inbound lead email

Create `SMHYNew@goodshowroom.com` and `SMHYUsed@goodshowroom.com` in the domain's Hostinger email administration. VPS access alone does not provision hosted mailboxes. Add their passwords securely to the shared backend environment as `HYUNDAI_INBOUND_NEW_PASSWORD` and `HYUNDAI_INBOUND_USED_PASSWORD`, then reload the backend with the normal deployment procedure. Do not put credentials into Git or the frontend environment.

The standalone backend polls INBOX every 60 seconds using TLS on port 993 at `imap.hostinger.com`. Usernames default to the addresses above; override with `HYUNDAI_INBOUND_NEW_USER`, `HYUNDAI_INBOUND_USED_USER` or `HYUNDAI_INBOUND_IMAP_HOST` if necessary. The Manager Dashboard's **Lead feed and email status** reports mailbox setup, connectivity and the latest source snapshot.

Emails create unassigned South Morang Hyundai prospects in New Leads, tagged New or Used according to the inbox. The manager can select **Website email** and **Unassigned** in Leads to allocate them. The dashboard shows each inbox's last successful check, imported email count, duplicate-merge count and manual-review count, refreshing every minute.

Dealer Studio's ADF 1.0 XML is accepted as the plain-text email body, including the XML and ADF processing instructions, or as a UTF-8 `lead.xml` attachment. The importer extracts customer names, mobile/email, vehicle year/make/model, request date, website reference, provider/service/URL, enquiry interest and customer comments. Customer phone numbers remain strings, preserving leading zeroes. The inbox decides the allocation category even when a vehicle's XML status differs. XML contains one prospect, a South Morang Hyundai vendor, a valid request date, vehicle year/make/model, and a named customer with a valid Australian mobile or email.

An ADF website reference is also used for replay protection, so resending the same website lead with a different email Message-ID does not create another customer. Labelled plain-text messages remain supported. The sender's address is never assumed to be the customer's address. Malformed XML, unsafe XML declarations, multiple prospects, missing required ADF fields and messages without recognized contact details produce durable manual-review receipts rather than blank customer records. The original email remains in its inbox. XML parsing is limited to 100 KB and rejects custom entity declarations.

The first poll imports existing INBOX messages, up to 50 per inbox per cycle. Imports use the email Message-ID for replay protection. Existing customer mobiles create manager merge reviews instead of duplicate customers. Messages over 10 MB produce a review receipt; review the original mailbox message manually. Polling never deletes, moves or marks messages as read. The checkpoint advances only after a durable receipt/import, including manual-review outcomes, so a malformed email cannot block later valid leads. UID validity changes restart scanning with message replay protection.

As an alternative to IMAP, a trusted email provider can POST to `/api/integrations/inbound-email/new` or `/used` with `Authorization: Bearer <HYUNDAI_INBOUND_EMAIL_SECRET>` (at least 32 random characters). JSON fields: `messageId` (required, stable), `subject`, `text`, `date` and optional `to` (must match the selected inbox). Keep this secret in server-side provider settings. Successful responses distinguish `imported` and `merge_review`; repeating the same message returns the existing receipt.

Verify with one synthetic email to each inbox after provisioning, then check the unassigned prospect, New/Used tag, captured details and mailbox connection status. Reprocessing the same Message-ID must not create another customer. Do not enable forwarding that loops messages back to these inboxes.

For a cluster at its collection quota, set `LEAD_STATE_COLLECTION=nexgate_sync` before the first release using these features. This stores mobile locks, merge requests, source links, email receipts and integration checkpoints in separate `gs:<kind>:` ID namespaces inside the existing operational collection. Nextgate seller checkpoints retain their existing IDs. Keep this setting consistent across processes and releases; changing it later requires migrating the state first. Customer records and messages stay in their existing collections.
